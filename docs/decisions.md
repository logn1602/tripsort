# Decision log

Settled project decisions and changes to the plan. Newest last.

| Date | Decision | Notes |
| --- | --- | --- |
| 2026-11-17 | Package name: `tripsort` | Free on PyPI as of 2026-11-17. |
| 2026-11-17 | Project license: MIT | Chosen over Apache-2.0 before Phase 1. |
| 2026-11-17 | Phase 1 publishes the 0.0.1 stub to PyPI as well as TestPyPI | The original plan published only to TestPyPI in Phase 1 and to PyPI from Phase 6. Every `v*` tag on `main` now goes to TestPyPI, is install-checked there, then goes to PyPI. |
| 2026-11-17 | Phase 1 runtime dependencies: `typer` only | The other core dependencies are added in the phase that first uses them. |
| 2026-11-18 | Phase 2 runtime dependencies: `numpy`, `pillow`, `pi-heif`, `imagehash`, `rich` | `opencv-python-headless`, `onnxruntime`, `scikit-learn`, and `platformdirs` arrive with the phases that use them. numpy 2.5, scipy 1.18 (through imagehash), and PyWavelets 1.10 need Python 3.12+, so `uv.lock` forks by Python version and 3.11 gets numpy 2.4, scipy 1.17, and PyWavelets 1.9. |
| 2026-11-18 | HEIC is decoded by `pi-heif`, not `pillow-heif` | pi-heif is the decode-only build (no x265 encoder in its wheels). `pillow-heif` is in the dev group only, to write HEIC test fixtures through its own API. Both claim Pillow's `HEIF` format, so tests never register pillow-heif, and a test checks the registered decoder is pi-heif. pi-heif 1.4.0 cannot decode HEIF thumbnails. A small type stub for pi-heif lives in `stubs/`. |
| 2026-11-18 | Each phase adds its own index migrations | `0001_initial.sql` creates only the tables Phase 2 fills; Phases 3 to 5 add theirs as `0002+`. The runner owns `schema_version`, applies each migration in one transaction, and refuses an index from a newer tripsort. |
| 2026-11-18 | Changes to the draft schema | `sources.fingerprint` (SHA-256 of the central directory listing) replaces `zip_sha256`: it identifies a zip in milliseconds, survives renames and moves, and lets a fully ingested zip be skipped without reading it. `occurrences` are keyed by `(source_id, member_index)` because one zip can hold the same name twice, and store the raw name bytes and the entry timestamp. `media` adds `format`, `has_exif`, `exif_datetime`, `exif_offset`, `exif_modified`, `exposure_time`, `iso`, and `note`, and drops `ext`. New tables: `skipped_members`, `exported_files`, `meta`. Columns only later phases fill, such as `is_front_camera`, come with those phases. |
| 2026-11-18 | Dates are resolved by `analyze` from raw facts | Ingest stores the EXIF time per file and the name and zip timestamp per occurrence; `analyze` picks EXIF, then file name, then zip timestamp. The result does not depend on zip order, and new name patterns apply without reading the zips again. Pixel `PXL_` names are read as UTC. A WhatsApp Desktop pattern (`WhatsApp Image YYYY-MM-DD at HH.MM.SS`) was added. `[time_offsets]` moves to Phase 4, its first user. |
| 2026-11-18 | Near-copy rule | Candidates need a similar aspect ratio (2%). When both files have EXIF capture times, the times must match and the pHash distance must be 2 or less, or 4 or less when their pixel sizes differ (burst shots are always the same size, while a storage-saver copy that kept its EXIF reached 4 in the eval); otherwise 6 or less (all initial). Files that name different camera models, files whose EXIF exposure time or ISO differ (each field counts only when both files record it, so true copies, which keep their EXIF, are never split), and same-size PNGs are never copies. Groups are stars around keepers instead of connected components, so a copy cannot chain two burst shots together. Measured first: burst-like siblings were as close as true copies (pHash 0 to 6). The same-size PNG rule was added after the eval merged two same-layout screenshots. The exposure and ISO rule was added for same-second bursts from cameras that record no sub-seconds; a locked burst (identical exposure and ISO) stays a known limit. |
| 2026-11-18 | The pHash input is box-reduced first | Decoding is unchanged (JPEG draft mode to about 1600 px), but the pHash is computed after an integer reduction to about 256 px on the short side, then the EXIF rotation. Resampling 1600 px straight to the 32 px the pHash uses cost about 100 ms per photo and changes nothing at the frequencies it keeps; ingest got about 7 times faster. |
| 2026-11-18 | Videos pass through until video support | MP4 and MOV files are exact-deduplicated and exported to `all/` without analysis, so 0.1.0a1 does not drop them. Live Photo MOVs are separate files until Phase 5 pairs them. |
| 2026-11-18 | Unreadable files go to `unreadable/` | Files whose bytes can be read but not decoded are exported to `unreadable/` for review and make the exit code 2. Entries that cannot be read at all (encrypted, Deflate64, damaged) are listed in the summary and `manifest.json` with advice, such as re-zipping without encryption. |
| 2026-11-18 | Oversized images pass through | Pillow's decompression-bomb check refuses 200 MP phone photos before draft mode can shrink them, so the supported formats are opened through Pillow's plugin registry without it. tripsort's own limit applies instead: the pixels actually decoded (after JPEG draft mode) must fit in `PIL.Image.MAX_IMAGE_PIXELS`. An image over it is exported and exact-deduplicated but gets no pHash. An embedded thumbnail is not used for the pHash: pi-heif cannot decode HEIF thumbnails, and oversized non-JPEGs rarely carry EXIF thumbnails. |
| 2026-11-18 | Export is incremental and only touches its own files | Assigned names are stored, so they do not shift when new zips arrive; collisions get `_1`, `_2`, compared case-insensitively after Unicode normalization. A later export writes only what is missing, removes files it wrote that are no longer wanted (only if unchanged since), leaves files edited after an export alone, re-creates files the user deleted, and never overwrites or deletes a file it did not write (an identical one is adopted, for example after `tripsort clean`). `--export-duplicates` writes `duplicates/<keeper>/` with the keeper hardlinked from `all/`. Exported files get the photo's date as their modified time. |
| 2026-11-18 | `manifest.json` has no absolute paths, GPS, or timestamps | Zips appear by file name only, so the output can be shared without revealing local paths or locations, and the same inputs and config give byte-identical manifests. An unchanged manifest is not rewritten. |
| 2026-11-18 | Usage errors exit with 1 | Typer exits with 2 on a bad command line; tripsort maps that to 1 so that 2 always means partial success. |
| 2026-11-18 | Google Takeout JSON dates move to a follow-up PR | Sidecar names are truncated and renamed several ways, a sidecar can sit in a different zip part than its photo, and the times are UTC with no zone. |
| 2026-11-18 | Dedupe metrics measure what ends up in `all/` | Precision: of the files left out of `all/`, the share whose photo is still in `all/`. Recall: the share of copies left out of `all/`. Pairwise grouping numbers are kept as diagnostics, since they also count which of two near-identical keepers a copy was filed under. With real photos as sources, a merge of two source photos has no ground truth (one may really be a WhatsApp copy of the other), so precision is reported as a range: counting each such merge as a mistake, and as correct. |
| 2026-11-19 | Keeper rule: an unedited file before a larger one | Most pixels, then has EXIF, then an EXIF modify date equal to the capture time (compared to the second, since cameras often record sub-seconds for the capture time only), then largest file, then SHA-256. The labeled real-photo eval showed that a same-size re-save of an already compressed photo can be larger than the photo itself and so become the keeper. An editor that re-saves a photo writes the time of the save as the modify date. A re-save that keeps the EXIF unchanged still goes by size. The eval's synthetic re-saves keep it unchanged, so the eval does not measure this step. The Software tag is not used, since phone cameras write one on originals too. When a HEIC original and a same-size JPEG conversion are both present, this usually picks the JPEG (the larger file, and it opens everywhere) unless the converter wrote a new modify date; documented in the README. |
| 2026-11-19 | Phase 3 runtime dependencies: `opencv-python-headless`, `scikit-learn`, `platformdirs` | OpenCV 5.1 runs YuNet and SFace through `cv2.FaceDetectorYN` and `cv2.FaceRecognizerSF`; scikit-learn 1.9 gives HDBSCAN, agglomerative clustering, and the eval metrics; platformdirs locates the model cache. scikit-learn ships no type hints, so a stub for the two clustering classes lives in `stubs/`. |
| 2026-11-19 | Face models: YuNet 2026may and SFace 2021dec, pinned to OpenCV Zoo commit `eb9f4f2` | `face_detection_yunet_2026may.onnx` is the 2023mar model re-exported with a dynamic input size, which the ONNX Runtime engine of OpenCV 5 needs, and OpenCV Zoo now lists it as the default. The files download on first use into `platformdirs.user_cache_dir("tripsort")/models` (or `TRIPSORT_MODEL_DIR`) and are checked against their size and SHA-256 every time they load. Without the models (offline), ingest still dedupes and exports, exits with 2, and a later ingest scans the photos it missed. |
| 2026-11-19 | Faces are found at ingest, in the same decode; every threshold applies in analyze | Detection runs on the image resized to 960 px. Each face is aligned from the larger decode (up to 2048 px), from a padded crop scaled so the face is about 112 px tall: small faces keep their detail, and large ones are shrunk with area averaging instead of the bilinear alignment warp alone (on the painting fixtures, same-painting similarity rose from 0.83 to 0.89 at the worst). Every detection down to score 0.5 is stored, up to 50 per photo, with box and landmarks as fractions of the oriented image. The detection score, foreground filter, clustering, naming, and background thresholds are `[people]` settings applied by analyze. Each face stores the face model id, which includes the detection size and a pipeline version; a new id rescans every photo. Photos indexed without faces (by 0.1.0a1, or while offline) are scanned by the next ingest, read back from the zips the index knows, and `tripsort ingest PROJECT` with no zips does only that. |
| 2026-11-19 | People are clustered from the foreground faces of kept photos only | A WhatsApp copy would count the same face twice. Faces are sorted by content hash before clustering, so the result never depends on zip order. |
| 2026-11-19 | Absolute checks around HDBSCAN | HDBSCAN's noise is relative: a face that is like nobody, or a group too small to form a cluster, can land in the nearest cluster. So a clustered face less than `member_min_similarity` (0.3, initial) similar to its cluster's average face is taken out, and a face left out joins the most similar cluster only when at least `attach_min_similarity` (0.5, initial) similar, never one that already has a face from its photo. These checks cannot separate two groups of similar size that HDBSCAN put together; the dev set measures how often that happens. HDBSCAN never returns exactly one cluster by default, so when it finds none it runs again allowing one (a trip with one recurring person). |
| 2026-11-19 | People keep their identity through their faces | Clusters are rebuilt whenever faces or settings change. Each face remembers its last person, and a new cluster becomes the person most of its faces belonged to. A person the user renamed, or merged others into, is pinned: every cluster mostly theirs stays theirs, so a merge survives new zips, and a cluster holding several pinned people is split between them. Any other person goes to the one cluster with most of their faces, so a stricter threshold can still split a person who was really two. person_NN numbers are never reused. A rename or merge makes the next export analyze again (index only), so background matches follow the edit. |
| 2026-11-19 | Naming from refs/ is one to one, and the user's names win | A name's reference is the mean of its photos' largest faces, embedded once and cached by SHA-256. Name and person pairs are taken from the most similar down, at least `ref_min_similarity` (0.4, initial) apart. A person the user renamed keeps that name, and a reference whose best match is such a person names nobody. The refs stay in the index until the next `--refs`. |
| 2026-11-19 | Background faces only count for named people | A background face counts for a named person at `background_min_similarity` (0.5, initial) or more. It adds the photo to that person's folder but never changes the shot type. |
| 2026-11-19 | Selfies come from the lens model until CLIP arrives | `is_front_camera` is read from `LensModel` ("front" as a word, as iPhones write it). A selfie is a front-camera photo with at least one foreground face, a flag on top of solo or group. The CLIP "a selfie" hint for phones that record no lens model comes with Phase 4. |
| 2026-11-19 | Phase 3 schema | Migration 0002 adds `face_scans` (a photo scanned with a model, even one without faces), `faces` (`person_id` is the last person a face belonged to, `match` says whether it belongs to them now), `people` (`number`, `name_key`, `named_by`, `pinned`), `ref_images`, and the media columns `is_front_camera`, `shot`, and `is_selfie`. It rebuilds `exported_files` so the roles `person` and `shot` are allowed. The draft `clusters` table is not used: cluster labels live on the faces, and average faces on the people. |
| 2026-11-19 | Review pages are deleted by clean | `tripsort people review` writes `review/people.html` with face crops read back from the zips and embedded in the page. `tripsort clean` deletes `review/` along with `.tripsort/`, since the crops are as private as the index. |
| 2026-11-19 | Category policy and v1 category list | One primary category per photo for folders, with all scores in the manifest; people and shot-type folders are independent. The v1 categories are scenery, animals, food, documents, and other. Labeling rule: if people are the main subject, the category is other; scenery means the view itself is the subject. Categories are labeled in the same pass as people and shot type. |
| 2026-11-19 | Face-model tests use public-domain paintings and run on every push | No photos of real people are in the repository. The `models` tests use three public-domain portrait paintings (Mona Lisa, Girl with a Pearl Earring, Gilbert Stuart's George Washington; sources in `tests/fixtures/README.md`), checking detection and same-painting similarity on flipped, cropped, darkened, brightened, and shrunk copies. Faces are a core feature now, so CI caches the model folder (keyed on the registry) and runs these tests on every push instead of nightly. |
| 2026-11-19 | People evaluation | `eval/run_eval.py prelabel` writes `labels.csv` and `labels.html` into the labeled set's folder, never the repository, and never overwrites a `labels.csv` unless forced. Only rows marked checked count. `people` scores one split (dev or test, 50/50 by SHA-256). Predicted people match labeled ones by name, then one to one by shared photos, so a person split in two counts the smaller part as missed photos. Names become p1, p2, ... and no file or folder names are printed or saved. |
| 2026-11-19 | Only the people with a ref are labeled | The labeler names themselves and a few friends, the people they have refs for, in every checked row, and leaves everyone else out: naming every stranger and friend in hundreds of photos is not practical. So the prelabel guesses list named people only, never person_NN. Predicted people that match no labeled person are counted but not scored. Every ref name is a labeled person, even one no checked row lists, so tripsort putting it on a checked photo that does not list it is a wrong photo; a name in the rows that matches no ref is counted, since it is most likely a typo. A labeled person found in a checked photo that does not list them is a wrong photo, whichever split holds their labeled photos. Homogeneity and completeness use only photos labeled solo with one labeled person and one foreground face found, so solo photos of unlabeled people are skipped, and so is a group photo where one labeled person is listed and only one face was found. The shot type counts everyone. |
| 2026-11-19 | Ref photos are checked against the labeled set | A ref photo that is one of the labeled photos would name that photo trivially and inflate the scores. With `--refs`, `prelabel` and `people` check each ref photo by SHA-256, by pHash within `phash_max_distance` (resized and re-saved copies), and by a face similarity of 0.9 or more (crops, edits, and burst neighbors, which a pHash misses; different photos of one person stayed at 0.81 or below in the labeled set). A flagged photo is given by position only: its name's place in alphabetical order, ignoring case, and its place among that name's photos. |
